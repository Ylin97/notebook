# 📚 大模型推理核心机制笔记（Prefill / Decode / KV Cache / TTFT / TPOT）

---

# 一、整体推理流程（Inference Pipeline）

一个标准的大模型推理请求流程如下：

```text
用户请求
   ↓
调度器排队（batching / queueing）
   ↓
Prefill（处理完整输入，构建 KV Cache）
   ↓
第一次 Decode（生成第一个 token） → TTFT
   ↓
Decode 循环（逐 token 生成）
   ↓
请求结束
   ↓
释放或复用 KV Cache
```

---

# 二、Prefill 与 Decode

## 1️⃣ Prefill（预填充阶段）

**定义：**  
对完整输入 prompt 一次性进行前向计算，并构建 KV Cache。

**特点：**

- 输入：完整序列
    
- 计算复杂度：O(n²)
    
- GPU 利用率：高
    
- 主要任务：构建 KV Cache
    

---

## 2️⃣ Decode（解码阶段）

**定义：**  
基于 KV Cache 逐 token 生成输出。

**特点：**

- 输入：单 token
    
- 计算复杂度：O(n)
    
- GPU 利用率：低（memory-bound）
    
- 主要瓶颈：显存带宽 + 通信
    

---

## ✅ 核心区别总结

|维度|Prefill|Decode|
|---|---|---|
|输入规模|全量 prompt|单 token|
|复杂度|O(n²)|O(n)|
|KV Cache|构建|使用 + 追加|
|性能瓶颈|算力|内存带宽|

---

# 三、Attention 与 KV Cache 原理

## 1️⃣ Attention 公式

$$
Attention(Q, K, V) = softmax\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

---

## 2️⃣ Q / K / V 的来源

```text
Q = X W_q
K = X W_k
V = X W_v
```

---

## 3️⃣ KV Cache 的本质

KV Cache 是 Transformer 在推理阶段缓存的：

- Key（K）
    
- Value（V）
    

用于避免重复计算历史 token。

---

## 4️⃣ KV Cache 数据结构（工程视角）

单层：

```text
K_cache: [batch, num_heads, seq_len, head_dim]
V_cache: [batch, num_heads, seq_len, head_dim]
```

整体：

```text
KV Cache = {
  layer_0: (K, V),
  layer_1: (K, V),
  ...
}
```

---

## 5️⃣ KV Cache 的计算过程

### Prefill 阶段：

```text
输入：x1, x2, ..., xn

K = [k1, k2, ..., kn]
V = [v1, v2, ..., vn]
```

---

### Decode 阶段：

只计算新 token：

```text
k_{n+1}, v_{n+1}
```

然后：

```text
K_cache = concat(old_K, k_{n+1})
V_cache = concat(old_V, v_{n+1})
```

---

### Attention 计算：

```text
Q_{n+1} × K_cache^T
```

---

# 四、核心性能指标

---

## 1️⃣ TTFT（Time To First Token）

**定义：**  
从请求发出到生成第一个 token 的时间

```text
TTFT = 排队时间 + Prefill + 第一次 Decode
```

👉 决定用户“响应快不快”

---

## 2️⃣ TPOT（Time Per Output Token）

**定义：**  
每生成一个 token 的平均时间

```text
TPOT = 总 decode 时间 / token 数
```

👉 决定生成速度

---

# 五、KV Cache 生命周期

---

## 1️⃣ 默认行为

```text
请求开始 → 创建 KV Cache
请求结束 → 释放 KV Cache
```

---

## 2️⃣ 为什么不能跨请求复用？

因为 KV Cache 绑定：

```text
token + positional encoding
```

只要 prompt 不同：

- token 不同 ❌
    
- 位置不同 ❌
    

→ cache 失效

---

## 3️⃣ 可复用场景（例外）

### ✅ Prefix Cache

相同前缀 → 复用 KV Cache

---

### ✅ 多轮对话

保留历史 KV Cache，追加新 token

---

### ✅ Streaming / Agent

KV Cache 长时间存在

---

# 六、KV Cache 的工程优化

---

## 1️⃣ Paged KV Cache（vLLM 核心）

问题：

- 连续内存 → 碎片严重
    

解决：

- 分页管理（类似操作系统）
    

优点：

- 动态 batch
    
- 显存利用率高
    

---

## 2️⃣ KV Cache 压缩

方法：

- FP16 → FP8 / INT8
    
- Multi-Query Attention（MQA）
    

效果：

- 显存占用显著降低
    

---

## 3️⃣ Sliding Window

只保留最近 token：

```text
丢弃旧 KV Cache
```

用于：

- 长上下文场景
    

---

## 4️⃣ KV Cache Pool

```text
释放 → 不销毁 → 放入池复用
```

作用：

- 减少 malloc/free
    
- 提升性能
    

---

# 七、分布式（TP）对推理的影响

---

## Tensor Parallel（TP）

特点：

```text
KV Cache 分布在多卡
```

问题：

```text
Decode 需要通信（all-gather / all-reduce）
```

影响：

- TP 越大 → TPOT 越高
    

---

# 八、调度机制（vLLM 关键）

---

## Continuous Batching（连续批处理）

执行方式：

```text
请求A：Prefill
请求B：Prefill
请求A：Decode
请求C：Prefill
请求B：Decode
...
```

特点：

- Prefill 和 Decode 混合执行
    
- 提升吞吐 + 降低 TTFT
    

---

# 九、常见工程问题

---

## ❌ 显存爆炸

原因：

- KV Cache 过大
    

解决：

- 限制 max_model_len
    
- 限制 batch
    
- 使用分页 KV Cache
    

---

## ❌ TTFT 过高

原因：

- Prefill 阻塞
    
- batch 过大
    

解决：

- continuous batching
    
- 分离 prefill / decode
    

---

## ❌ Decode 很慢

原因：

- memory-bound
    
- KV Cache 太长
    

解决：

- KV 压缩
    
- 减少上下文长度
    

---

## ❌ TP 越大越慢

原因：

- 通信开销主导
    

---

```text

模型记忆

```

# 十一、面试速答模板（强烈建议背）

---

### Q：什么是 KV Cache？

> KV Cache 是 Transformer 推理阶段缓存的 attention 中间结果（Key 和 Value），其形状通常为 `[batch, heads, seq_len, head_dim]`。在 Prefill 阶段构建，在 Decode 阶段复用，从而避免重复计算历史 token，将复杂度从 O(n²) 降低到 O(n)。

---

### Q：Prefill 和 Decode 区别？

> Prefill 对完整输入执行全 attention 计算并构建 KV Cache，复杂度为 O(n²)；Decode 基于 KV Cache 逐 token 生成输出，复杂度为 O(n)，但需要多轮迭代，性能瓶颈在内存访问。

---

### Q：KV Cache 为什么不能复用？

> KV Cache 与 token 序列和位置编码强绑定，只要 prompt 发生变化，其 attention 结构就不同，因此无法直接复用，除非前缀完全一致。

---

### Q：TTFT 和 TPOT？

> TTFT 是首 token 延迟，反映响应速度；TPOT 是每 token 生成时间，反映生成速度。
